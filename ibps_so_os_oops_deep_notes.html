Process Concept, Thread & Multithreading

Start here — every scheduling and synchronization question assumes you're fluent in what a process and a thread actually are.

Process vs Program

Definition

Program = passive entity, just code sitting on disk. Process = active entity — a program in execution, with its own memory (text, data, heap, stack), CPU registers, and resources.

Process Control Block (PCB)

The kernel data structure holding everything the OS needs to manage a process. Frequently tested as a "which of these is NOT stored in the PCB" question.

▸PCB fields to memorise
▾
  • Process ID (PID), Process state
  • Program Counter (PC) — address of next instruction
  • CPU registers (accumulator, stack pointer, general registers)
  • CPU scheduling info — priority, pointers to scheduling queues
  • Memory management info — base/limit registers, page/segment tables
  • Accounting info — CPU used, time limits, process number
  • I/O status info — list of open files, allocated devices
Exam trap: A Context Switch (saving the old process's PCB, loading the new one's) is pure overhead — no useful computation happens during it. Higher context-switch frequency ⇒ more overhead, not more throughput.

Thread

Definition

A thread is the basic unit of CPU utilisation — a "lightweight process". It has its own Program Counter, register set, and stack, but shares code, data, and OS resources (open files) with other threads of the same process.

Why threads matter (benefits): Responsiveness, Resource sharing, Economy (cheaper to create/switch than a full process), Scalability (uses multiple cores).

Multithreading models

ModelMappingLimitation / Benefit
Many-to-OneMany user threads → 1 kernel threadSimple, but one blocking syscall blocks all threads; no true parallelism
One-to-OneEach user thread → its own kernel threadMore concurrency, but thread creation is costlier (Windows, Linux use this)
Many-to-ManyMany user threads → smaller/equal kernel threadsFlexible — best of both, developer isn't limited by kernel thread count

Multithreading vs Multiprocessing: multithreading runs multiple threads inside one process sharing memory space; multiprocessing runs multiple independent processes with separate memory — heavier, but more isolated/fault-tolerant.

Process Scheduling

The single most numerically-tested OS topic — expect both concept MCQs and Gantt-chart-style waiting/turnaround time calculations.

Schedulers — three types

SchedulerRoleFrequency
Long-term (Job Scheduler)Selects which processes are admitted into the ready queue; controls degree of multiprogrammingRuns infrequently (seconds/minutes)
Short-term (CPU Scheduler)Selects which ready process runs next on the CPURuns very frequently (milliseconds)
Medium-termSwaps processes in/out of main memory to manage loadRuns occasionally

Scheduling criteria (know the formulas)

Key formulas

Turnaround Time = Completion Time − Arrival Time
Waiting Time = Turnaround Time − Burst Time
Response Time = Time of first CPU allocation − Arrival Time

Goals: maximise CPU utilisation & throughput; minimise turnaround time, waiting time, and response time.

CPU scheduling algorithms

AlgorithmPreemptive?Key ideaWeakness
FCFSNoRuns processes strictly in arrival orderConvoy effect — short jobs stuck behind one long job
SJFOptional (SRTF if preemptive)Shortest burst time runs first — provably minimises average waiting timeNeeds burst time prediction; can starve long jobs
Priority SchedulingEitherHighest priority process runs firstCan starve low-priority processes (fixed via aging)
Round RobinYesFixed time quantum, cycles through ready queueQuantum too small → excess context switching; too large → behaves like FCFS
Multilevel QueueVariesSeparate queues per process type (e.g. foreground/background), each with its own algorithmRigid — a process can't move between queues
Multilevel Feedback QueueYesLike above, but processes can move between queues based on behaviour/agingMost flexible, but complex to configure

Deadlock & Synchronization

Two of the most conceptually rich OS topics — and a reliable source of "which of these is/isn't a condition" style questions.

Deadlock — the four Coffman conditions

A deadlock can occur only if all four of these hold at once:

1. Mutual Exclusion

At least one resource must be held in a non-shareable mode.

2. Hold and Wait

A process holds at least one resource while waiting to acquire more.

3. No Preemption

A resource can only be released voluntarily — it can't be forcibly taken away.

4. Circular Wait

A closed chain of processes exists, each waiting for a resource held by the next.

Exam trap: "Preemption" itself is NOT a deadlock condition — the actual condition is No Preemption. Watch for this exact wording flip in options.

Handling deadlocks

StrategyApproach
PreventionDesign the system to negate at least one of the four conditions
AvoidanceBanker's Algorithm — before granting a request, check if the resulting state is "safe" (a completion order exists for all processes)
Detection & RecoveryAllow deadlock to occur, detect it (wait-for graph / resource-allocation graph), then recover by terminating a process or preempting a resource
IgnoranceOstrich algorithm — assume it won't happen; used by most general-purpose OSes (e.g. UNIX) since deadlocks are rare in practice

Banker's Algorithm needs three matrices: Max (max demand), Allocation (currently held), and derives Need = Max − Allocation, checked against the Available vector.

Synchronization

Definition

Race condition: the final outcome depends on the timing/interleaving of concurrent access to shared data — the classic bug synchronization prevents.

Critical Section — three requirements

▸Mutual Exclusion, Progress, Bounded Waiting
▾
  • Mutual Exclusion — only one process may execute in its critical section at a time
  • Progress — if no process is in the critical section, one of the processes waiting to enter must be allowed to, without indefinite postponement
  • Bounded Waiting — there's a limit on how many times other processes can enter before a waiting process gets its turn

Tools for synchronization

ToolDetail
Peterson's SolutionSoftware-only solution for 2 processes using a turn variable and a flag[] array
Binary SemaphoreValue restricted to 0 or 1 — behaves like a mutex lock
Counting SemaphoreCan take any non-negative integer — controls access to a resource with multiple instances
Mutex LockSimple lock/unlock mechanism; ownership is tied to the locking thread

Semaphore operations: wait() / P() decrements the value (blocks if it goes negative); signal() / V() increments it (wakes a waiting process).

Classic synchronization problems

  • Producer-Consumer (Bounded Buffer) — producers add items, consumers remove them, from a fixed-size shared buffer
  • Readers-Writers — multiple readers can access shared data simultaneously, but writers need exclusive access
  • Dining Philosophers — 5 philosophers, 5 forks; the textbook illustration of how naive resource-locking causes deadlock

Memory Management, Paging, Segmentation, File System & Protection

Five syllabus topics that all revolve around one question: how does the OS give each process the illusion of its own private memory and files?

Memory management basics

Logical vs Physical address

The CPU generates a logical (virtual) address; the MMU (Memory Management Unit) translates it into a physical address — the actual location in RAM.

Fragmentation typeCause
InternalAllocated block is slightly bigger than needed — wasted space sits inside the partition
ExternalEnough total free memory exists, but not as one contiguous block — fixed via compaction

Swapping — temporarily moving a process out of main memory to a backing store (disk) and back, to free up space for other processes.

Paging vs Segmentation

FeaturePagingSegmentation
Division basisFixed-size blocks (pages/frames)Variable-size, logical program divisions (code, data, stack)
Address formPage number + OffsetSegment number + Offset
Table usedPage table (page → frame)Segment table (base + limit per segment)
External fragmentationNonePossible (variable sizes)
Internal fragmentationPossible (last page)None
Speed-up hardwareTLB (Translation Lookaside Buffer) caches recent page-table lookups—
Exam trap: Paging avoids external fragmentation; Segmentation avoids internal fragmentation. These get swapped in options constantly — memorise the pairing, not just the words.

File System

File allocation methods:

MethodAccessTrade-off
ContiguousSequential + directFast, but external fragmentation and hard for a file to grow
LinkedSequential onlyNo external fragmentation, but pointer overhead and a broken pointer corrupts the rest of the chain
IndexedDirect + sequentialUses an index block of pointers — no external fragmentation, small overhead per file

Directory structures: Single-level → Two-level → Tree-structured → Acyclic-graph → General graph (increasing flexibility, increasing complexity).

Free space management: Bit vector (bitmap, 1 bit per block), Linked list of free blocks, Grouping, Counting.

System Protection

Goal

Ensure every process accesses only the resources it's authorised for, per a defined policy — protection is about enforcing correct use, distinct from security's focus on external threats.

Access Matrix: rows = domains, columns = objects, cells = permitted operations. Implemented practically as either:

  • Access Control List (ACL) — stored per object: which domains can access it and how
  • Capability List — stored per domain: which objects it can access and how

OOPs — deep dive

Exactly the five pillars on your syllabus sheet — Classes/Objects/Methods, Encapsulation, Abstraction, Polymorphism, Inheritance — covered with the distinctions the exam actually probes.

Classes, Objects & Methods

Class

A blueprint/template that defines what attributes (data) and behaviours (methods) its instances will have. A class itself occupies no memory for object data until instantiated.

class Car { String model; // attribute void drive() { } // method }

Object

A concrete instance of a class, with its own state (attribute values), behaviour (methods it can perform), and identity (a unique reference/address distinguishing it from other objects of the same class).

Car myCar = new Car(); // myCar is an object of class Car myCar.model = "Sedan";

Methods & self / this

Functions defined inside a class that operate on that object's data. C++/Java use the implicit keyword this to refer to the current instance; Python requires it explicitly as the first parameter, conventionally named self.

Encapsulation vs Abstraction — the most-confused pair

Encapsulation — the "how"

Bundles data and the methods that act on it into one unit, restricting direct outside access via access modifiers. It's an implementation-level hiding technique — "data hiding".

private double balance; public double getBalance() { return balance; }

Abstraction — the "what"

Hides implementation complexity, exposing only essential features. It's a design-level hiding technique, achieved via abstract classes and interfaces — "complexity hiding".

abstract class Shape { abstract double area(); // what, not how }
Memory trick: Encapsulation = wrapping a capsule around data (hides data). Abstraction = an architect's blueprint (hides complexity). Both "hide" something, but not the same thing.

Inheritance — all five types

TypeStructureSupport
SingleOne parent → one childC++, Java, Python
MultilevelGrandparent → Parent → Child chainC++, Java, Python
HierarchicalOne parent → multiple childrenC++, Java, Python
MultipleOne child ← multiple parentsC++, Python (direct); Java only via interfaces
HybridA combination of the aboveC++, Python; Java approximates via interfaces
Exam trap — the Diamond Problem: when a class inherits from two classes that share a common ancestor, it's ambiguous which version of an inherited method to use. Java sidesteps this entirely by disallowing multiple inheritance through classes; C++ resolves it with virtual inheritance.

Polymorphism — compile-time vs runtime

Compile-time (Static) Polymorphism

Resolved by the compiler based on method signature — Method Overloading and Operator Overloading.

int add(int a, int b); double add(double a, double b); // same name, different signature

Runtime (Dynamic) Polymorphism

Resolved at runtime via dynamic dispatch — Method Overriding, which requires an inheritance relationship. This is what lets a parent-type reference call the correct child-specific behaviour.

Shape s = new Circle(); // parent reference, child object s.area(); // runs Circle's overridden area(), decided at runtime
