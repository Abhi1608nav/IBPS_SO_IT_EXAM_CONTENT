process.txt

Software Process

What Software Engineering actually is, why it emerged as a discipline, and the generic activities every process is built from.

Definition

Software Engineering is a systematic, disciplined, and quantifiable approach to the design, development, operation, and maintenance of software — applying engineering rigor to software creation instead of ad-hoc coding.

The Software Crisis — why this discipline exists

A term coined in the late 1960s for a cluster of recurring problems in early software projects: budgets and schedules blown, poor-quality and inefficient software, systems failing to meet requirements, and code that became unmanageable to maintain. This led directly to the 1968 NATO Software Engineering Conference, which formally established "software engineering" as its own discipline.

Generic Process Framework Activities

▸The 5 core activities every process shares
▾
  • Communication — gathering requirements and understanding the problem from stakeholders
  • Planning — creating a roadmap: scope, resources, risk, schedule
  • Modeling — building analysis and design models to understand the problem and plan a solution
  • Construction — code generation and testing
  • Deployment — delivery to the customer and collection of feedback

Umbrella Activities

These span the entire process rather than belonging to any single phase: project tracking & control, risk management, Software Quality Assurance (SQA), formal technical reviews, measurement, documentation, reusability management, and change management.

Exam framing: if a question describes an activity that "happens throughout the project, not at one specific stage" (e.g. risk management or SQA), it's an umbrella activity, not one of the five core framework activities.

SDLC Models

The single most-tested Software Engineering topic. SDLC = Software Development Life Cycle: Requirement Analysis → Design → Implementation → Testing → Deployment → Maintenance. What varies between models is how these phases are arranged.

Waterfall Model

Strictly linear-sequential — each phase must fully complete before the next begins.

Strengths

Simple to understand and manage; thoroughly documented at every stage; works well for small projects with clear, stable requirements.

Weaknesses

No working software until very late; extremely costly to revisit an earlier phase once signed off; poor fit for evolving requirements.

Exam trap: the single most-repeated Waterfall weakness — it has no feedback loop back to earlier phases and does not accommodate changing requirements.

V-Model (Verification and Validation Model)

An extension of Waterfall where every development phase is explicitly paired with a corresponding testing phase, forming a "V" shape when drawn.

v_model_pairing.txt
Requirements Analysis ↔ Acceptance Testing System Design ↔ System Testing Architecture / HLD ↔ Integration Testing Module / Detailed Design ↔ Unit Testing

Best for reliability-critical systems (medical, aerospace, banking). Still shares Waterfall's core rigidity — poor at handling changing requirements.

flow · v_model.svg — left arm = verification, right arm = validation

Incremental Model

The system is built and delivered as a series of increments (builds), each one adding new functionality on top of the last. Each increment is developed roughly like a mini-waterfall. Advantage: working software reaches users early and grows piece by piece.

flow · incremental_model.svg — each increment ships and adds scope

Iterative Model

Starts with a rough, partial implementation and refines it through repeated cycles.

Iterative vs Incremental — the exact distinction the exam tests: Iterative refines the same core functionality repeatedly across cycles. Incremental adds new functionality with each release. These two get swapped in options constantly.
flow · iterative_model.svg — same scope, repeated refinement

Spiral Model (Boehm)

Combines iterative development with explicit, systematic risk analysis — this is the model's defining feature. Each loop around the spiral has four quadrants:

  1. Determine objectives, alternatives, and constraints
  2. Identify and resolve risks
  3. Develop and test (build the next-level product)
  4. Plan the next iteration
Quick recall: Spiral = the risk-driven model. If a question mentions "risk analysis at every cycle," the answer is Spiral, not Iterative.
flow · spiral_model.svg — each loop repeats all 4 quadrants, spiralling outward

Prototype Model

A quick, working prototype is built from currently known requirements purely to gather user feedback before full-scale development begins.

  • Throwaway prototyping — the prototype is discarded once requirements are clarified
  • Evolutionary prototyping — the prototype is refined and evolves directly into the final system

Best suited to projects where requirements are unclear or poorly understood at the start.

flow · prototype_model.svg — loops until the customer accepts

Agile Model

Iterative + incremental, built around flexibility, customer collaboration, and rapid delivery in short cycles called Sprints (typically 2-4 weeks).

The Agile Manifesto — 4 core values (memorise these exactly)

1. Individuals and interactions over processes and tools
2. Working software over comprehensive documentation
3. Customer collaboration over contract negotiation
4. Responding to change over following a plan

Popular frameworks built on Agile principles: Scrum, Extreme Programming (XP), Kanban.

Exam trap: Agile explicitly embraces changing requirements, even late in development — the exact opposite of Waterfall's philosophy. This contrast is a favourite comparison question.
flow · agile_sprint_cycle.svg — one sprint, repeated every 2-4 weeks

RAD (Rapid Application Development)

Emphasises fast delivery through heavy component reuse, minimal upfront planning, and continuous, close user involvement. Best for projects with well-defined business requirements and a scope small enough to finish quickly.

flow · rad_model.svg — parallel component teams compress the timeline

Requirement Engineering

How raw stakeholder needs become a formal, testable specification.

Definition

The process of gathering, analysing, documenting, and managing software requirements throughout the life of a project.

The 5 Requirement Engineering activities

▸Elicitation → Analysis → Specification → Validation → Management
▾
  1. Requirement Elicitation — gathering requirements via interviews, questionnaires, brainstorming, use cases, direct observation
  2. Requirement Analysis — checking requirements for consistency, completeness, feasibility; resolving conflicts between stakeholders
  3. Requirement Specification — formally documenting requirements, typically in an SRS document
  4. Requirement Validation — confirming with stakeholders that the documented requirements are correct and complete
  5. Requirement Management — handling requirement changes over the remaining life of the project

Functional vs Non-Functional Requirements

Functional

Define WHAT the system should do — specific features and behaviours. E.g. "the system shall allow users to reset their password."

Non-Functional

Define HOW WELL the system performs — the "-ilities": Performance, Security, Usability, Reliability, Scalability, Maintainability, Availability.

Exam trap: "The system must respond within 2 seconds" sounds like a specific behaviour, but it's a Non-Functional requirement (Performance) — it describes quality of service, not a feature.

SRS (Software Requirement Specification) — the 7 IEEE characteristics of a good SRS

CharacteristicMeaning
CorrectAccurately represents the actual requirements
UnambiguousOnly one possible interpretation
CompleteIncludes all significant requirements
ConsistentNo conflicting requirements
VerifiableTestable and measurable
ModifiableStructured for easy updates
TraceableEach requirement traces back to its origin and forward to design/test artifacts

Feasibility Study

Conducted before requirement engineering fully proceeds, to decide whether the project is even worth pursuing:

Technical

Can it be built with current technology and available skills?

Economic

Is it cost-justified? (cost-benefit analysis)

Operational

Will it actually be used and accepted by the organisation?

Schedule

Can it be completed within the required timeframe?

Software Design Principles

Not on your explicit topic list, but Coupling & Cohesion get tested constantly alongside SDLC and Software Process — worth having ready.

Coupling — interdependence between different modules

Lower is better — more independent modules are easier to maintain, test, and reuse.

1ContentOne module directly modifies/relies on another's internals — worst
2CommonModules share global data
3ExternalModules share an externally imposed data format/protocol
4ControlOne module controls another's logic via passed flags
5StampModules share a composite data structure, using only parts of it
6DataModules exchange only simple, necessary parameters — best

Cohesion — how well elements WITHIN one module belong together

Higher is better — a module doing one well-defined thing is easier to understand and reuse.

1CoincidentalElements grouped arbitrarily, no real relationship — worst
2LogicalGrouped because they're logically similar/categorised together
3TemporalGrouped because they execute at the same time (e.g. "initialization")
4ProceduralGrouped because they follow a certain execution order
5CommunicationalGrouped because they operate on the same data
6SequentialOutput of one element feeds directly into the next
7FunctionalEvery element contributes to one single, well-defined task — best
The rule tested every time: good design = LOW coupling + HIGH cohesion. If an option describes tightly-linked modules or a module doing unrelated things, it's describing bad design.
debugging.txt

Debugging

What happens after testing finds a problem.

Debugging vs Testing — the core distinction: Testing finds whether/where a defect exists (detects a failure). Debugging happens next — it locates the root cause of that failure and fixes it. Testing comes first; debugging follows.

Debugging approaches

ApproachHow it works
Brute ForceUses memory dumps, print/trace statements to observe program state — least efficient, but the most commonly used in practice
BacktrackingTraces backward from the point of failure toward its origin, step by step — works for small programs, becomes impractical as size grows
Cause EliminationLists possible "cause hypotheses," then designs tests to systematically eliminate each until the true cause is isolated
Program SlicingNarrows the search to only the code that could possibly affect a specific variable's value at the point of failure

Modern IDE debuggers implement these ideas via breakpoints, watch variables, and step-through execution — letting a developer pause and inspect program state at any point.

Software Testing

The biggest topic after SDLC Models — verification vs validation, testing levels, black/white box, and the specialised test types that get confused constantly.

Verification vs Validation

Verification

"Are we building the product RIGHT?" — checks the software conforms to its specifications. Done throughout development via reviews, walkthroughs, inspections. Mostly static — no code execution.

Validation

"Are we building the RIGHT product?" — checks the software meets actual user needs. Done via dynamic testing — actually executing the software.

Exam trap: this exact "right product" vs "product right" phrasing is one of the most repeated SE questions in banking exams — don't mix up which one is which.

Levels of testing (in order)

LevelTestsDone by
Unit TestingIndividual components/modules in isolationDevelopers
Integration TestingInteraction/interfaces between integrated modulesDevelopers/QA
System TestingThe complete, fully integrated system against overall requirementsQA team
Acceptance TestingSystem against business/user requirements before deliveryClient/end users

Integration testing approaches: Big Bang (integrate everything at once), Top-down (start from top-level modules, use stubs for lower ones), Bottom-up (start from lower-level modules, use drivers for upper ones), Sandwich/Hybrid (combination of both).

Acceptance testing split: Alpha Testing — done in-house, by the organisation's own internal team, in a controlled environment. Beta Testing — done by real end users, in a live environment, before public release.

Black Box vs White Box vs Grey Box

TypeKnowledge of internalsTechniques
Black BoxNone — tests functionality onlyEquivalence Partitioning, Boundary Value Analysis, Decision Table Testing
White BoxFull — tests internal logic/structureStatement Coverage, Branch/Decision Coverage, Path Coverage, Condition Coverage
Grey BoxPartialA mix of both approaches

Specialised test types — the ones that get mixed up

TypePurpose
Regression TestingRe-tests after a code change to confirm nothing that worked before has broken
Smoke TestingA quick, broad and shallow check that a new build is stable enough for further testing — run FIRST
Sanity TestingA quick, narrow and deep check of one specific area after a small change/fix
Load TestingSystem behaviour under expected/normal load
Stress TestingSystem behaviour under extreme load, beyond normal capacity — finds the breaking point
Performance TestingMeasures speed, responsiveness, and stability under a given workload
Usability TestingEvaluates how easy/intuitive the software is for real users
Smoke vs Sanity — the most confused pair: Smoke = broad + shallow, run on every new build before deeper testing begins. Sanity = narrow + deep, run on one specific feature right after a minor fix.

Test Case & Test Oracle

Test Case

A defined set of inputs, execution conditions, and expected results, designed to verify one specific test objective.

Test Oracle

The mechanism or source used to determine the correct expected output — how you actually know whether a test passed or failed.

CASE Tools

CASE = Computer-Aided Software Engineering — the tools that support and automate development activities.

Definition

Software tools that support and automate software development activities — requirement analysis, design, coding, testing, and project management.

Types of CASE tools

TypeSupports
Upper CASEEarly-stage activities — requirement analysis, high-level design (diagramming/modeling tools)
Lower CASELater-stage activities — coding, testing, debugging, maintenance
Integrated CASE (I-CASE)The entire SDLC end-to-end, in one connected toolset

Benefits

  • Improved productivity and faster development
  • Better, more consistent documentation
  • Improved software quality (fewer errors slip through)
  • Reduced long-term maintenance cost
  • Enforced standardisation across a team

Common examples: UML modeling tools, version control systems (Git), automated testing frameworks, project management/tracking tools.

Bonus — Software Estimation (COCOMO): frequently paired with SDLC topics. Boehm's COCOMO (COnstructive COst MOdel) estimates effort from project size in KLOC (thousand lines of code), using Effort = a × (KLOC)^b, with constants depending on project type:
TypeDescription
OrganicSmall team, simple/familiar project, well-understood requirements
Semi-detachedMedium size/complexity, mixed team experience
EmbeddedComplex, tight constraints (hardware/regulatory/real-time), highly innovative

Function Point Analysis (FPA) is the alternative — it measures software size from its functionality (inputs, outputs, inquiries, files, interfaces) rather than lines of code, making it language-independent unlike LOC-based estimation.
